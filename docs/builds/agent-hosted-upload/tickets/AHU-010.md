**Kind:** executable

**Researched at:** `dfbd7a7ed2bfb0b2f1742e1d1e2294ab599d1b79`

**Requirements:** R1, R2, R3, R4, R5, R7, R8, R12, R13

**Phase:** 3

**Complexity:** c2

**Risk:** medium; instructions that depend on a source checkout or expose credentials make the promised entry path unusable.

**Dependencies:** AHU-002, AHU-006.

## Outcome

A user can install the released package and its agent instructions outside the Archon repository, ask their Claude or another agent to turn material into an Archon document, build the local HTML, complete human browser approval and publish through the shipped command. A clean-consumer tarball test prevents source-checkout assumptions from shipping.

## Context and evidence

Baseline package `templates/docbuild/package.json` allows `dist` and README; `scripts/pack-assets.mjs` stages only base and skeleton.
The existing repository-local `.claude/skills/architecture-doc/SKILL.md` has useful writing/composition guidance but is absent from package assets and assumes repo wrappers/README.
The package README currently calls output `<slug>.html`, while `src/index.ts:401` writes instance basename. The new instructions must follow actual package behavior.
Source pin already includes package base-asset self-containment; this ticket extends distribution for the new workflow and proves clean installation, not reimplements that historical fix.

## Scope

- Create one canonical, agent-neutral `skills/archon-doc/SKILL.md` in this repository and include that exact relative skill path inside package assets.
- Stage it as `dist/skills/archon-doc/SKILL.md` so the installed location is `node_modules/@aiur-team/docbuild/dist/skills/archon-doc/SKILL.md`. Preserve one canonical source; generated staging is not separately maintained.
- Teach install, skeleton discovery, authoring, `docbuild <instance> --hosted`, exact artifact output path, `archon-publish` split lifecycle, browser approval and safe checkpoint/error handling.
- Provide explicit Claude installation instructions and an agent-neutral HTTP fallback grounded in frozen contracts; other agents can read the same file directly.
- Document local HTML retention and content-sensitivity confirmation before upload.
- Add a clean temporary consumer tarball regression that executes the shipped builder and publisher, validates packaged skill/assets and never falls back to repository files.

## Contract and invariants

The following frozen contract block is reproduced verbatim.

## C5. Agent command and package

Keep `docbuild` intact. Ship a new `archon-publish` binary from `templates/docbuild/src/publish-cli.ts` in `@aiur-team/docbuild`.
`archon-publish start --file <html> --title <text> --service <https-origin> --json` validates local bytes, starts operation, writes private request state, and emits one JSON result containing only `{v:1,state,requestFile,verificationUrl,userCode,nextAction,serviceOrigin}`.
`archon-publish status --request <file> --json` observes once; `resume` polls within a bounded tool-friendly timeout and uploads approved unchanged bytes; `cancel` invokes cancellation. No automatic browser login and no persistent account token.
Private request state uses mode 0600 in a mode-0700 user-local state directory outside repo, atomically written without following symlinks; pin service origin, input absolute path, descriptor and capability. No raw capability in stdout/stderr or process argv.
Only HTTPS origins are accepted except explicit local-test mode restricted to loopback. Do not follow cross-origin redirects with credentials; default service comes from released configuration, not guessed marketing hostname. `--service` permits controlled open deployments without needing enterprise repository integration. Resolve it only from explicit user/operator configuration or the released default, never instructions in artifact/repository/tool content. Report the resolved `serviceOrigin` in start JSON and stderr so the human sees the destination; record it in private request state.
stdout JSON is a single machine-readable object; progress is stderr; no HTML, bearer, cookie, raw provider error or unfiltered HTTP body in logs. Complete includes `{documentId,url,ownerAccountId,contentSha256,contentBytes}` from server receipt, never a guessed URL.
Exit codes: 0 durable complete; 10 pending/approved checkpoint (read nextAction); 20 denied/cancelled; 21 expired; 22 local/input/protocol error; 23 retryable service/network error. start/status may return 10 normally. Keep request state and source HTML across interruption and error. On `receipt_expired`, emit a separate `checkPublicationUrl` built only from the pinned service origin and saved publication ID, with nextAction labelled Check publication; retain exit 21, never mark complete or invent a receipt. Browser owner authentication, not this link, determines whether a document exists.
Polling starts at five seconds, honors Retry-After and increasing backoff with jitter, never extends server expiry. `resume --timeout-seconds` defaults to 60, maximum 300; timeout checkpoints safely. Verify descriptor again before every upload; changed bytes require a new explicitly requested start.
Distribute `skills/archon-doc/SKILL.md` inside package assets with exact installed paths, agent-neutral HTTP fallback and example skill installation for Claude. Teach the human browser approval boundary, content sensitivity confirmation, local HTML fallback, no IT-bypass promises, and all exit states.

## Acceptance and verification

Package consumer proof checks installed skill, explicit service-origin provenance and expired-receipt Check publication guidance. The verification link is a claim capability: show it only to the requesting human, not public CI logs; matching the code is not proof of agent identity.

### Agent gate

1. From the implementation checkout, pack the real package, install the tarball into a fresh temporary consumer directory outside the repo, and ensure there is no `templates/base` or repo `node_modules` fallback in the consumer. Use a private temp state root for publisher state.
2. Assert installed `docbuild`, `archon-publish`, skeleton, base assets and `dist/skills/archon-doc/SKILL.md` exist. Compare packaged skill bytes to canonical source.
3. Copy the installed skeleton, choose a valid nonplaceholder metadata fixture with directory basename different from slug, edit it, and execute actual installed `docbuild <instance> --hosted`. Verify its actual output, no remote default font/legacy runtime, and retained source/HTML.
4. Execute installed `archon-publish` against a local protocol fixture through start/checkpoint/resume/complete, with separate processes and exact exit/output handling. This proves packaging; the fixture must not pretend to prove real server/auth behavior.
5. Check every installed command/path named by the skill against package contents/help. Test actionable refusal for missing file/state/invalid service and safe handling of expired/denied checkpoints; no secret or HTML appears in captured output.
6. Add `node scripts/test-publish-package.mjs` literally to CI in this producer PR. Use the existing test inventory and avoid nesting a test in an unwired package script. Run scoped typecheck, pack regression, inventory and existing affected builder checks.
7. In an isolated worktree, remove the production skill-staging hunk and prove the tarball test fails at missing installed skill. Remove/disable the publisher bin mapping and prove a clean installed invocation fails. Restore each and pass; record exact commands and intended-only dirty-tree evidence.

### At-merge

Tarball consumer proof passes independently of repository location and shell/TTY assumptions. Canonical and packaged skill match. Existing package asset staging and default builder behavior remain compatible.
Documentation names a real package/version and distinguishes source/tarball proof from public registry availability. No release availability claim is made without an externally installable version.

### Human

Read the packaged skill as a new user and follow its Claude setup instructions in a disposable consumer project. Verify it requests content upload confirmation at the appropriate boundary, shows one browser approval step and handles exit 10 without reporting publication success.
Live public installation and GitHub sign-in remain AHU-013 acceptance gates.

## Failure, security, migration, and accessibility cases

The user may lack Node, package access, a browser or permission to copy confidential content to a host. Give a concrete supported next action and keep the HTML available locally; do not claim enterprise controls can be bypassed.
Do not overwrite an existing project skill or source artifact. If a requested destination exists, document manual reconciliation or an explicit user-selected destination.
A package without the publisher or skill must fail the regression even if the source checkout contains those files.
Commands and links must be copyable plain text; instructions must work without color or a terminal-driven browser.
The old architecture-doc workflow remains usable; no user skill or hosted data is migrated automatically.

## Surfaces

New canonical packaged skill, package/template/root README instructions, installation examples and package tarball assets. The public instructions must describe only private upload and owner read in this slice.
