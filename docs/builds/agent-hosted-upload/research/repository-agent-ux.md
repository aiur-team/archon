## Agent-facing primitive and lifecycle

Recommendation: one installed command whose simplest form publishes an existing HTML file, with explicit resumable operations for agents that cannot keep a tool call alive during browser sign-in. These are **proposed interface shapes**, to be finalized in the shared contract ticket:

```text
archon publish artifact.html --title "Design review"
archon publish start artifact.html --title "Design review" --json
archon publish status --request-file <local-request-path> --json
archon publish resume --request-file <local-request-path> --json
archon publish cancel --request-file <local-request-path> --json
```

The exact package/command spelling is a planning decision, not an existing executable. Keeping the upload command in the existing `@aiur-team/docbuild` package is the smallest distribution change if adding a second `bin` remains coherent; a separate package is reasonable only if the plan assigns its release/install workflow. Do not promise `npx archon` until a package and registry owner are established.

Every browser-supported publishing operation should have the documented HTTP primitive and machine-readable result underneath it. The browser alone signs in and approves or denies. Agents do not drive the OAuth form, receive the GitHub access token, or use browser session cookies. A direct HTTP client should be able to complete the upload after the same handoff; the skill is guidance over the protocol rather than privileged magic.

The recommended state progression is local validation → pending browser authorization → approved → durable upload result. Denied, expired, cancelled, retryable service error, and definitive input error are separate outcomes. `status` must be observational; reconnecting to a request must not implicitly generate another document or nominate a different owner. The browser should name the artifact, size, requesting device/process context where useful, and signed-in GitHub account before approval.

Start should persist a mode-0600 request file before printing a resumable browser link. The file contains request identity, artifact digest/size, service origin, expiry, and private polling/upload authority; create parent state directories mode 0700. Do not store under the user's repository by default or require that a generated HTML file be deleted after uploading. The request file path can be printed; its contents and bearer credentials cannot. Verify file identity and avoid following a symlink or overwriting unrelated state. Retain enough completed receipt metadata for repeat `resume` after a lost final response.

The authorization URL must contain only public handoff identity/user code, not the private polling secret. JSON stdout should contain only safe state metadata, next action, local artifact/request paths, browser URL, and final document URL. Human progress goes to stderr; `--json` should never mix progress prose with one JSON result. Terminal error codes must distinguish expiry/denial/cancellation, invalid local input, service unavailable/retryable, and durable success; define actual codes once in the contract. Never echo raw HTTP bodies, headers, GitHub OAuth errors containing credentials, HTML input, or private request-file contents.

An optional convenience wait command should respect the server's polling interval/slowdown and bounded deadline, print the browser link immediately, and stop cleanly on interrupt while keeping resumable state. Split-phase start/status/resume avoids making successful user sign-in depend on one agent tool timeout. A 429 needs server-directed retry scheduling; a 5xx should not be labeled denial or expiry.

Bind authorization and idempotency to exact artifact bytes/digest and size, with title treated as display metadata. If the artifact changes after approval, require a new publish operation. For an ambiguous upload timeout, resume with the original operation authority and return the same server receipt. Define whether a completed receipt remains queryable after upload authorization expires; the lost-response acceptance case otherwise fails at the expiry edge. Agents must not infer success by constructing a URL from a client-selected ID.

## Bounded ticket seams and merge order

These seams are recommendations for the main planning agent to map into the final DAG; they are not a second ticket inventory.

1. **Shared hosted contracts and deployment boundary.** Add versioned request/response/state schemas, namespace/routes, limits, errors, ownership and isolation decisions; establish actual service modules and deployment import seams only if consumers can use them. Own central routing/config/gate test changes here. A documentation-only contract can precede parallel producers but is not production functionality.
2. **Identity and browser authorization.** Stable GitHub account/session, OAuth callback binding, approval/denial UI, and publishing request binding. Tests must drive handler state plus browser-facing account/approval output. New files such as `netlify/lib/hosted-identity.mjs` and `netlify/lib/hosted-identity.test.mjs` are proposed, not existing. Avoid changing legacy identity semantics globally.
3. **Publishing operation state and durable upload.** Pending/approved/completed lifecycle, hashed private capability, create-only/CAS commit record, immutable artifact storage and replay receipt. Proposed `netlify/lib/hosted-publish.mjs`, `netlify/lib/hosted-publish.test.mjs`, and `netlify/functions/hosted-publish.mjs`. May need separate protocol-state and storage producers if the final design warrants them; never split merely by nouns when neither yields testable behavior.
4. **Owner reader and HTML isolation.** Authenticated document shell, raw-byte authorization, isolated rendering, cache headers, denial pages; use current `app.js` interactions as render acceptance. Proposed `scripts/test-hosted-reader-browser.mjs` plus service unit tests. Depend on stable identity and stored-document schema; cannot merge a readable public blob path before the owner gate.
5. **Agent publishing client and portable instruction distribution.** Installed binary, start/status/resume/cancel lifecycle, bounded HTTP, local state security, error/output contract; packaged skill and precise install/build/publish examples. Proposed `templates/docbuild/src/publish.ts`, `templates/docbuild/src/publish-cli.ts`, `templates/docbuild/src/publish.test.ts`, `scripts/test-publish-package.mjs`. CLI can develop against a contract fixture while server producers run, but acceptance must later hit their real endpoints. If skill/setup packaging merits a separate ticket, it depends on the actual published command contract.
6. **Hosted builder profile if selected.** Add an explicit upload/offline profile excluding legacy collaboration auto-connect and remote fonts, retain theme/navigation, leave existing builds identical. Proposed additions in `templates/docbuild/src/index.ts`, `cli.ts`, `layout.html`, tests. Serialize relative to client edits in the same CLI/package if both are separate tickets. Avoid broad refactoring of the builder or making unrelated `--site` fix a prerequisite.
7. **End-to-end release proof and operator setup.** Exercise a freshly packed/installed client from outside the repository, real browser authorization, durable upload, owner rendering, different-user denial, interrupted retry, active HTML isolation, and source artifact retention. Provisioning steps/required secrets/domains are operator work; do not substitute fixture tests for deployed OAuth proof. A disposable hosted test requires explicit authorized infrastructure setup and must identify its cleanup targets.

For every seam, meaningful regression tests belong to its producer PR. A later integration ticket composes them; it does not own all testing. Proposed test files must be named in `.github/workflows/check.yml` as soon as introduced. Sharing that file is a soft edit conflict that can use additive step ownership and merge refreshes; shared service schema, route dispatch, `cli.ts`, package metadata, and runtime template edits may require real hard dependency/serialization.

- Run the existing root lockfile install/module-load gate in its pre-build order. New server imports cannot depend on generated builder `dist` existing.
- Test CLI stdout/stderr through a real spawned binary and a local HTTP fixture, not only exported helpers. Include malformed response, cancellation, backoff, expiry, interrupted operation, changed artifact, lost response/retry, and token redaction assertions.
- Test package consumption using `npm pack` followed by a clean temporary consumer install with no `templates/` checkout available. Copy shipped skeleton, use differing directory/slug, build, and execute the new command. Assert the installed skill path exists and references commands actually in the tarball.
- Existing docbuild tests use Node's built-in runner after TypeScript compilation; new `.test.ts` files must be explicitly named using `templates/docbuild/dist/<name>.test.js` in CI. Existing netlify identity tests use Node VM module isolation; following that approach avoids live provider/global-state reads.
- Existing browser regression runners (`scripts/test-p4-k-browser.mjs`, `scripts/test-p4-l-browser.mjs`) provide a local fixture/Playwright pattern. Avoid inventing an unrelated UI test stack unless the new service topology requires it.
- No package publication workflow appears in the tracked workflow inventory; source packaging does not prove npm availability or provide release authority. Assign operator publication as a launch gate with exact package version or support installation from a release tarball until publication exists.

## Open decisions

1. Is the first supported input arbitrary self-contained HTML, builder-generated HTML, or both? Recommendation: accept bounded single HTML bytes as the upload contract and teach the Archon builder as the preferred creation path. Owner-read v1 need not demand edit/history sidecars. This avoids importing the much stricter legacy connect contract accidentally.
2. Where is the public agent instruction hosted and how is it installed for Claude versus other agents? Recommendation: a canonical packaged skill plus a public human-readable quickstart, with clear explicit installation paths and a direct HTTP fallback. Avoid assuming cloning all of Archon is required.
3. Which package owns the publisher binary, and is its selected version available to external users? Source establishes `@aiur-team/docbuild@0.0.1`; registry publication is unverified.
4. Does the new service use this repository's existing Netlify site or a separately configured deployment? Existing gate/cache/frame behavior and current self-hosted connect copying constrain co-location. The deployment decision must precede tickets specifying routes.
5. Does hosted rendering need scripts? Theme/nav and arbitrary interactive artifacts benefit from scripts, but legacy collaboration modules should stay unavailable. Final CSP/sandbox/network policy must come from security research rather than inheriting old site defaults.
6. What survives authorization expiry for recovery of already-durable publication? The protocol must provide a bounded receipt recovery rule without granting open-ended upload capability or creating duplicates.
